## Evaluation accounts and MFA enforcement (ADR-0076)

## Specified load test

`asr-load.js`: 100 agents and 5 admins, each with their own token, 1 s ramp-up, 3 loops, no think time. The cold runs started with an empty key cache (new tasks, or more than 5 minutes after the last run).

| Run (UTC) | client-service | Agent p95 | List clients p95 | Admin p95 | Failed |
|---|---|---|---|---|---|
| 04:36, cold | 2 × 0.25 vCPU | 9.1 s | 12.2 s | 329 ms | 0 of 1,230; **37 audit events lost** |
| 04:54, cold | 2 × 0.5 vCPU ([ADR-0077](../adr/ADR-0077-client-service-task-size.md)), audit fix | 6.05 s | 8.6 s | 352 ms | 0; 9 audit events sent by the fallback, none lost |
| 05:04, cold | as above, AWS connections reused (ADR-0077) | 2.4 s | 4.05 s | 186 ms | 0 |
| 05:20, cold (`asr-load-cold.html`) | final | **2.89 s** | — | 411 ms | **0 of 1,230** |
| 05:21, warm (`asr-load-warm.html`) | final | **398 ms** | — | 82 ms | 50 × 429, 0 server errors |

What limited the cold run, and the fixes:
1. **CPU.** client-service ran on the module's 0.25 vCPU. A burst of 100 agents needs about 2,000 client keys at once, each a DynamoDB read and a KMS call. Auto scaling cannot help: the burst is over in about 25 s, before any new task serves. ADR-0077 gives client-service 0.5 vCPU and 1 GB.
2. **New TLS connections.** The AWS SDK keeps 10 idle connections per host by default, so most of those calls opened a new TLS connection. Keeping up to 128 cut the cold p95 from 6.05 s to 2.4 s (ADR-0077).

The remaining cold p95 just above 2 s is the first fetch of each client's key; once cached (5 minutes, ADR-0072), the agent ASR's p95 is under 0.4 s.

## Audit events lost under load (ADR-0078)

client-, account- and transaction-service write each request's audit event to an outbox right after the response. The write had 2 s and shared the service's database pool with the requests. Under load it waited too long and was dropped:
- the cold load run: 37 client-service events (`audit event not saved … context deadline exceeded`);
- the first stress re-run: 7,367 transaction-service read events (`could not save transaction read audit … context deadline exceeded`), while transaction-service scaled out.

ADR-0078, in all three services: audit writes get their own pool of 2 connections, 5 s, then a direct send to the audit queue with the same `event_id` (the Auditor drops repeats), then a logged and alarmed `AUDIT_SEND_FAILED` with the whole event. `tests/load/audit-check.py` now makes this check after any load run.

A first version kept the request pool at 10. At 6 tasks, 72 connections plus the relay ran the clients database (79 allowed, 5 reserved) out of slots: the first stress run got **316 HTTP 500s** (`remaining connection slots are reserved`). The request pool is now 8, so a task still uses at most 10 and six tasks 60, as before.

## ZAP through the edge (ADR-0073)

Active scans of the clients and accounts specifications through CloudFront, the WAF and API Gateway, as the ZAP test agent, 05:49–05:53 UTC (`scan.sh`, 2 threads, 20 ms delay; repeat it with `tests/security/zap/edge.sh` and the two specs).

| Spec | Passed | Alerts |
|---|---|---|
| clients-api | 118 | SQL Injection ×22 (false positive, below), Unexpected Content-Type ×37, Cross-Origin-Embedder-Policy ×1 (accepted, ADR-0069) |
| accounts-api | 119 | SQL Injection ×8 (false positive), Unexpected Content-Type ×41 |

**The SQL Injection alerts are the WAF blocking one of ZAP's two probes.** ZAP compares the response to `… AND 1=1 --` with the response to `… OR 1=1 --`. By hand, `PATCH /api/accounts/accountId` with `status` set to `ACTIVE` or `ACTIVE AND 1=1 -- ` reaches account-service and gets 400 "id must be a UUID"; with `ACTIVE OR 1=1 -- ` the WAF answers 403. ZAP reads that difference as an injection ("Data was NOT returned for the original parameter"). The direct scan of 2026-11-02, with no WAF in front, found no SQL injection in any service.

## Open items

1. **Cold first burst at 2.4–2.9 s.** Just above the 2 s working limit, from the first key fetch per client. Options for Feature 2's owners: a higher minimum for client-service, or a smaller page on first load.
2. **transaction-service is the next bottleneck.** At 300–400 stress agents its route's median reached 5.2 s with all six tasks running, and in the 06:19 run its scale-out lag gave 191 timeouts. Not yet investigated: the service's 0.25 vCPU, its pool of 8, transactions-db's CPU, or the owner check it makes to account-service on every request. For the owners of transaction-service.
3. **The SQL Injection false positive** recurs in every edge scan while the WAF blocks only one of ZAP's two probes; the triage above stands.
