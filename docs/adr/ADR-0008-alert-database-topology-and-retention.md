## Context

The feature needs transactional state, deduplication, reproducible scoring, and
retention controls. A separate Multi-AZ RDS instance per service would conflict
with the feature and project cost caps.

## Decision

Use a dedicated `event_alert` PostgreSQL database and least-privilege database
role on the approved shared lower-environment PostgreSQL cluster. Tables are owned
only by the alert service; other services use APIs/contracts. Production topology
must be re-evaluated before staging if shared-cluster isolation is insufficient.

Flyway owns forward-only migrations. UUIDs are generated by the application;
money and scores use fixed-precision numeric columns; timestamps are UTC. Unique
constraints enforce source-result and client-event idempotency. Optimistic
versions protect decisions. News metadata, model prompts/responses, and briefs
expire after 90 days; audit records remain in the auditor for one year. Cleanup is
bounded, observable, and never deletes audit evidence.

Backups follow the shared cluster policy. Restore testing must prove that replay
does not duplicate alerts or decisions. Destructive schema changes use an
expand/migrate/contract sequence across releases.

## Consequences

This minimizes cost while maintaining logical ownership, but cluster-level blast
radius is shared. Credentials, migrations, connection limits, backup ownership,
and staging topology must be confirmed with the infrastructure owner.

## Validation

Migration, isolation, retention, backup/restore, concurrency, and duplicate-key
tests are required before staging.
