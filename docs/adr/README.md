# Architecture Decision Record Index

Use this index to identify which ADRs are relevant before loading their full
text. A one-line summary is a routing aid, not a replacement for an applicable
ADR; humans and agents must read the complete record before making or reviewing
a decision it governs.

## Accepted decisions

- [ADR-0001](ADR-0001-user-directed-push-policy.md) — PRs are the default, while warned and explicitly authorized direct integration is allowed only for unprotected task and feature branches.
- [ADR-0002](ADR-0002-direct-dev-governance-updates.md) — Azeez authorizes narrowly scoped Git-workflow and agent-instruction updates directly to `dev`, subject to file allowlisting, warning, synchronization, and non-forced-push checks.
- [ADR-0003](ADR-0003-maintain-one-line-adr-index.md) — Every ADR must have a one-line entry in the ADR index, which agents scan for relevance before reading applicable decisions in full.
- [ADR-0004](ADR-0004-event-driven-alerts-mvp-charter.md) - Feature 4 is Event-Driven Client Alerts, owned by Azeez and Hayyun with approved MVP scope, data boundaries, guardrails, retention, and budget defaults.
- [ADR-0004](ADR-0004-auditor-kafka-to-sqs-migration.md) — Auditor service messaging migrates from Kafka to Amazon SQS (standard queue plus DLQ), superseding the "no message broker" note in `docs/architecture/nfr-notes.md`.
- [ADR-0005](ADR-0005-cognito-security-across-features-1-and-2.md) — Features 1 and 2 share Cognito identity, with service-side JWT validation and Agent-owned client/account authorization.
- [ADR-0006](ADR-0006-transaction-account-linkage-and-access.md) — Feature 3 links imports to CRM account UUIDs and serves authenticated transaction reads through User-service, with account ownership checked by client-profile (decisions 1–2 superseded by ADR-0037: transactions have their own database and are linked through account-service; decision 4 superseded by ADR-0035: ownership is now checked by account-service).
- [ADR-0017](ADR-0017-microservices-per-business-area.md) — One microservice and database per business area (accounts split from clients), with Go allowed for the auditor, client-service and account-service.
- [ADR-0020](ADR-0020-audit-write-path-outbox-shared-sqs.md) — Extends ADR-0004: services with a database write each audit event to their own outbox in the business transaction (existing request-middleware producers may save it right after the request, because of the cost of changing them), and a relay sends it to the shared `audit-insert` queue; transaction ingest writes its event in the import's transaction; Cognito triggers fail open.
- [ADR-0035](ADR-0035-account-ownership-across-services.md) — account-service copies each account's owning agent from client-service at creation using the caller's token, checks ownership locally, and client-service refuses to delete a client with accounts; both checks fail closed; supersedes ADR-0006 decision 4 (decision 4 partly superseded by ADR-0036: only undeleted accounts block a client's deletion).
- [ADR-0036](ADR-0036-soft-deletion-of-clients-and-accounts.md) — Deleting a client or account sets `deleted_at` and keeps the row; deleted records are hidden from everyone and are not the same as `closed` accounts; uniqueness ignores deleted rows; deleting is not erasure; supersedes ADR-0035 decision 4 in part.
- [ADR-0037](ADR-0037-transactions-database-and-account-linking.md) — Transactions get their own database; the import links rows to accounts through account-service's `/internal/accounts/lookup`, authenticating with a Cognito client-credentials token, and fails closed; supersedes ADR-0006 decisions 1–2.
- [ADR-0033](ADR-0033-xf2-dashboard-topology-cache-audit.md) — X-factor 2: stateless dashboard-service fanning out with the caller's JWT, a 3-minute per-caller cache, and best-effort audit events.
- [ADR-0038](ADR-0038-dashboard-metric-definitions.md) — X-factor 2: what each dashboard figure means; only figures the data supports exactly, no sums across currencies, deleted records never counted, no composite agent score.
- [ADR-0030](ADR-0030-client-data-envelope-encryption.md) — client-service encrypts the 11 personal client fields with per-client data keys kept in DynamoDB and wrapped by KMS, so deleting a key erases the client; email and phone stay unique through blind indexes keyed by one shared KMS HMAC key over normalised values.
- [ADR-0021](ADR-0021-audit-read-path-grpc-service-connect.md) — The auditor is internal-only and checks every caller's token; one changes-only activity feed in user-service (`GET /api/activities`) shows admins all agents' activities and agents their own, read over gRPC through ECS Service Connect; tamper findings are left to ADR-0022.
- [ADR-0022](ADR-0022-audit-tamper-resistance-and-crypto-shredding.md) — A hash chain over every field of each audit row and its parent's hash; an auditor database role that can only insert and read; a daily run-once chain-verify task that records each problem once in a findings table and anchors the head in S3 Object Lock; crypto-shredding for erasure.
- [ADR-0040](ADR-0040-cognito-triggers-java-lambda.md) — The Cognito login and password-reset triggers are one plain Java 25 Lambda at 1,769 MB (no SnapStart; measured cold start about 0.5 s), sending `COGNITO_TRIGGERS` events within a 3-second budget, never failing the sign-in, and logging failed sends for a replay tool.
- [ADR-0025](ADR-0025-identity-cognito-mfa-pkce-service-tokens.md) — Extends ADR-0005: mandatory MFA, managed login with PKCE (S256) from a public app client, client-credentials service tokens, Cognito triggers for login auditing, and sign-outs reported by the frontend to user-service (audit call first) for logout auditing.
- [ADR-0041](ADR-0041-client-identity-documents-and-manual-verification.md) — Identity documents (JPEG, PNG or PDF, up to 5 MB) are uploaded through client-service, encrypted with the client's data key and stored in a private SSE-KMS bucket; uploading never verifies; documents are optional for Verify, which records who verified, when and which documents, and records and shows a verification without one as such; no request is sent to the client.
- [ADR-0024](ADR-0024-transaction-ingestion-sftp-lambda.md) — Import transactions from a self-hosted external SFTP server with a scheduled VPC-attached Lambda written in Go (extending ADR-0017's exception), JSON files, a ready-file protocol, idempotent inserts, rejected unsupported and unparseable files, and retries with a circuit breaker on the connection.
- [ADR-0046](ADR-0046-human-deploy-access-mfa-role.md) — Operators deploy as the hand-made role `crm-infra-admin` (administrator, MFA required, 4-hour sessions), assumed from IAM users in `crm-deployers` whose keys can reach nothing else; Identity Center is impossible in this member account, and Terraform cannot hold a role that its teardowns would destroy.
- [ADR-0051](ADR-0051-engagement-service-and-mail-dispatcher.md) — Agent engagement runs in a new Java 25 `engagement-service` with its own `db.t4g.micro` database and stack; a dispatcher in every task claims queued mail with `FOR UPDATE SKIP LOCKED` and a lease, so two tasks never claim the same row, delivery is at least once, and nothing is sent while the stack is stopped (extends ADR-0017 and ADR-0023).
- [ADR-0052](ADR-0052-calendar-invites-by-email.md) — Agents' calendars get CRM meetings through emailed iCalendar invites (`METHOD:REQUEST` and `CANCEL`, stable `UID`, rising `SEQUENCE`), one-way, with the agent as the only attendee and no OAuth or provider APIs.
- [ADR-0053](ADR-0053-email-delivery-through-ses.md) — All engagement email goes through SES from `mail.<legal_entity>.<domain>` with DKIM, MAIL FROM and DMARC, kept in a long-lived `stacks/mail-identity`; agents' addresses come from Cognito `ListUsers` by `sub`, clients' from client-service at send time and are never stored; sandbox recipients only for the demo (decisions 1, 3 and 9 partly superseded by ADR-0055: without the domain's hosted zone, mail comes from one verified address).
- [ADR-0054](ADR-0054-ai-follow-up-drafts-and-holiday-data.md) — Follow-up drafts come from Amazon Nova Micro, called through Bedrock Runtime in Singapore with its Asia-Pacific cross-region profile (never a global one), using placeholders and public holiday data only, pass a strict safety screen or fall back to a template, sit behind a kill switch and caps, and are sent only by the agent; holidays come from a versioned table seeded by migrations (decision 6 partly superseded by ADR-0056: agents edit plain text; decision 8 partly superseded by ADR-0057: new Singapore years synced from data.gov.sg).
- [ADR-0055](ADR-0055-sender-address-without-a-domain.md) — In an account without the domain's hosted zone, engagement mail comes from one verified SES address, `sender_address`, set in both `stacks/mail-identity` and `stacks/agent-engagement`, with no DNS records and no DKIM alignment; with a domain, ADR-0053 is unchanged (supersedes ADR-0053 decisions 1, 3 and 9 in part).
- [ADR-0056](ADR-0056-drafts-edited-as-plain-text.md) — Agents edit follow-up drafts as plain text: the service fills in the client's first name and the agent's name when returning a draft, and marks each whole-word occurrence as its placeholder again when saving, so drafts are still stored without names; saving needs client-service and Cognito (supersedes ADR-0054 decision 6 in part).
- [ADR-0057](ADR-0057-holiday-sync-from-data-gov-sg.md) — engagement-service adds newly published Singapore public holidays from MOM's consolidated data.gov.sg dataset at start-up and daily, adding rows only, checking every name, and alarming on a missing next year or a mismatch; the calendar offers no month after the last covered year (supersedes ADR-0054 decision 8 in part).

## Proposed decisions

Target-architecture ADRs, described in [`docs/architecture/system-overview.md`](../architecture/system-overview.md). Numbering starts at 0017 because feature branches already use 0001–0016.

- [ADR-0005](ADR-0005-alert-holdings-and-valuation-boundary.md) - Use service-owned synthetic holdings and reproducible, freshness-aware valuation snapshots for the alert MVP.
- [ADR-0006](ADR-0006-alert-processing-architecture.md) - Run bounded scheduled ECS batches with PostgreSQL idempotency and no new alert-specific broker.
- [ADR-0007](ADR-0007-alert-service-runtime-boundary.md) - Build one Java 25 Spring Boot module with separately enabled API and worker modes.
- [ADR-0008](ADR-0008-alert-database-topology-and-retention.md) - Use an isolated alert database on the approved shared lower-environment PostgreSQL cluster with Flyway and bounded retention.
- [ADR-0009](ADR-0009-agentcore-search-region-and-fallback.md) - Restrict public Web Search 1.2.0 to a governed Tokyo Gateway with quotas, kill switch, and no automatic fallback.
- [ADR-0010](ADR-0010-alert-ai-provider-and-safety.md) - Use Luna behind a public-data-only structured adapter that abstains on unsafe or invalid output.
- [ADR-0011](ADR-0011-alert-news-content-governance.md) - Allow only reviewed official sources, retain minimal cited metadata, and support correction and takedown.
- [ADR-0012](ADR-0012-alert-api-event-and-authorization-contracts.md) - Freeze versioned alert APIs/events with ownership-scoped agents and read-only admins.
- [ADR-0013](ADR-0013-alert-audit-delivery-and-failure-policy.md) - Use a transactional outbox and explicit fail-closed/queued-audit behavior for tamper-resistant audit delivery.
- [ADR-0014](ADR-0014-alert-observability-cost-and-kill-switches.md) - Add redacted metrics, hard quotas, budget alarms, and independent ingestion/model kill switches.
- [ADR-0015](ADR-0015-deterministic-alert-materiality-scoring.md) - Use versioned fixed-decimal exposure and materiality rules that fail closed on unusable valuations.
- [ADR-0016](ADR-0016-holdings-derived-search-universe.md) - Derive bounded public search terms from sufficiently common client holdings inside Singapore without exporting portfolio facts.
- [ADR-0018](ADR-0018-ecs-fargate-compute.md) — Run all services and scheduled tasks on ECS Fargate across two AZs with 1–6 tasks per service, rejecting EKS on cost and effort.
- [ADR-0019](ADR-0019-edge-entry-chain.md) — Enter through CloudFront with WAF, then API Gateway HTTP API (JWT check, throttling), a VPC Link and a private internal ALB.
- [ADR-0023](ADR-0023-rds-per-service-backup-no-cache.md) — One RDS PostgreSQL instance per service with a Multi-AZ standby, AWS Backup with a cross-region copy, and no cache tier.
- [ADR-0026](ADR-0026-one-stack-per-legal-entity.md) — Segregate data by deploying one full Terraform stack per legal entity; only Singapore is deployed.
- [ADR-0027](ADR-0027-observability-baseline.md) — Structured PII-masked logs, CloudWatch metrics and dashboard, alarms to SNS with named owners, GuardDuty and CloudTrail.
- [ADR-0028](ADR-0028-cicd-migrations-terraform.md) — GitHub Actions deploying through OIDC; schema migrations with Flyway in an init container in each service's task, before its app starts, which also gives every service its own login without schema rights; and all infrastructure in Terraform.
- [ADR-0029](ADR-0029-environment-lifecycle-and-cost-controls.md) — Local dev, disposable staging, prod only for the final weeks, and Multi-AZ only in the demo week, to stay under USD 300.
- [ADR-0031](ADR-0031-xf1-alert-processing-search-region-boundary.md) — X-factor 1: a worker every 4 hours sends only public terms to AgentCore web search in Tokyo; summaries use Bedrock in Singapore; own alerts-db.
- [ADR-0032](ADR-0032-xf1-instrument-master-deterministic-matching.md) — X-factor 1: deterministic instrument master and matching with no vector similarity; search only instruments held by ≥ 2 clients and ≥ 5% of clients.
- [ADR-0034](ADR-0034-xf3-health-monitor-rules-and-bedrock-boundary.md) — X-factor 3: deterministic rules in a daily 08:00 SGT task, with Bedrock in Singapore used only for wording and a template fallback.
- [ADR-0039](ADR-0039-dashboard-aggregate-endpoints.md) — X-factor 2: owning services serve dashboard figures on private `/aggregates` routes scoped by the caller's token and not audited there; agents' transaction totals go through user-service.
- [ADR-0042](ADR-0042-terraform-deployment.md) — Terraform layout and S3 state with native locking, for an account on the paid plan (a Free-plan mode was tried and dropped); NAT gateways removed between sessions, and every service redeployed on each start or stop so its tasks get every Service Connect name, which requires creating stacks stopped; certificates written into tasks by an init container; Service Connect proxies TLS ports as TCP (supersedes ADR-0021 decision 5 in part on acceptance); a domain registered by hand in Route 53 puts the app on its own name and the internal ALB on HTTPS; every service behind the ALB serves TLS; no service connects as its database's master user.
- [ADR-0043](ADR-0043-client-and-transaction-list-endpoints.md) — `GET /api/clients` lists an agent's own clients or, for an admin, every client, paged; `GET /api/transactions` lists all linked transactions for admins only through user-service, cursor-paged; both audited (Q&A UM04, TM14).
- [ADR-0045](ADR-0045-producer-account-list-synced-from-crm.md) — The simulated bank's producer reads its account list from a file on the SFTP server on every run and publishes nothing when it is empty; `scripts/sync-producer-accounts.sh` copies the CRM's open, non-deleted accounts into it through SSM Run Command, so the producer never calls the CRM (extends ADR-0024 decision 1).
- [ADR-0047](ADR-0047-business-dashboard-terraform-stack.md) — dashboard-service moves from `stacks/crm` into its own `stacks/business-dashboard`, which reads the CRM stack's `dashboard_inputs` output through `terraform_remote_state`, owns its image repository, security group and rules on the CRM's service groups, and is allowed on the audit queue through `extra_audit_producer_role_arns` (amends ADR-0042 decision 1).
- [ADR-0050](ADR-0050-accounts-pending-until-client-verified.md) — An unverified client's new accounts open as Pending (account-service reads `verification_status` from the client lookup it already makes and refuses other statuses with 403); after verifying, the agent may make them Active, and `PATCH /api/accounts/{id}` lets the owning agent change a verified client's account to any status, audited with its before and after values; admins do not manage client accounts (supersedes ADR-0035 decision 2 in part on acceptance).
- [ADR-0058](ADR-0058-every-deployment-ends-with-full-teardown.md) — Every deployment starts from an empty account and ends by destroying every Terraform stack, `mail-identity` and `bootstrap` included; stopping is only a pause within a deployment; one deployment at a time; budget alerts are made by hand outside Terraform: USD 200 at 10, 20, 40, 60, 80 and 100%, and USD 25 a month for Bedrock (supersedes ADR-0053 decision 2, ADR-0042 decision 1 and ADR-0029 in part).

## Maintenance rule

Add or update exactly one concise entry whenever an ADR is added, superseded, or
has its status changed. Keep historical entries and identify the superseding ADR
rather than deleting an old decision from this index.
