# ADR-0021: Audit reads: internal-only auditor, gRPC through ECS Service Connect

## Context

Admins and agents view activity: a client's history, the admin-wide view of all agents' activity, and the admin view of tamper findings. That data lives in the auditor's audit-db. The audit store is the most sensitive data set in the system and must be tamper-resistant, and the spec says audit logs are for administrators (with agents seeing a filtered view of their own clients; [open item 1](../architecture/open-items.md#1-agent-visibility-of-activity)). Reads need an immediate, paged answer.

## Decision Drivers

- Security: minimise the audit store's network exposure (NFR 8)
- Request/response semantics for reads
- Load balancing of long-lived connections across tasks in two AZs (NFR 1, NFR 2)
- A typed, versioned contract between Go and Java (NFR 3)

## Options Considered

### Option A: REST on the auditor, routed through the ALB to the browser

- Pros: simple; directly usable by the frontend.
- Cons: exposes the tamper-resistant store to the internet path; the auditor would own presentation for several business contexts.

### Option B: reads through SQS (request and reply queues)

- Pros: reuses the audit queue infrastructure.
- Cons: reads need an immediate answer; request/reply over queues adds latency and complexity.

### Option C: internal gRPC through ECS Service Connect (chosen)

- Pros: the auditor stays internal-only; owning services present activity views over their own REST APIs; a typed `.proto` contract; Service Connect's Envoy balances calls over healthy tasks.
- Cons: an extra hop through the owning service; TLS and certificate handling for gRPC.

## Decision

- The **auditor is internal-only**: no ALB route, no public endpoint.
- Activity views are REST endpoints on the owning services, documented in their OpenAPI specs: client history in client-service (`GET /api/clients/{id}/activity`), the admin-wide view in user-service (`GET /api/activities`, Admin only), and the admin view of tamper findings in user-service (through a new auditor gRPC method, for example `ListTamperFindings`).
- Those services call the auditor over **gRPC** through **ECS Service Connect** (alias `auditor:50051`, `appProtocol: grpc`).
- **Zero Trust on every call:** the auditor's security group admits only named callers; callers forward the user's JWT in gRPC metadata and the auditor validates it and enforces role filters (Admin: any activity; Agent: own clients only); background callers use a Cognito client-credentials token with an `audit/read` scope.
- **TLS** end to end with a certificate from a project CA generated by Terraform; the server sets `keepalive.MaxConnectionAge` (about 5 minutes) so connections rebalance.
- **Resiliency:** about 2-second deadlines, retry only on `UNAVAILABLE`, circuit breakers (Resilience4j in Java, gobreaker in Go); if the auditor is down, views show "history temporarily unavailable".
- **Contract:** `.proto` in a shared `proto/` directory, package `audit.v1`, additive changes only, paged responses; CI runs `buf lint` and `buf breaking`.

## Rationale

Keeping the auditor internal removes it from every internet-facing path. gRPC suits request/response reads and gives one generated contract for Go and Java. Service Connect is needed because plain DNS or a layer-4 load balancer would pin each caller's long-lived HTTP/2 connection to one task.

## Consequences

### Positive

- Minimal exposure of the audit store; business context stays in the owning services.
- Contract breaks are caught in CI.
- Business actions are unaffected by auditor outages (writes go through SQS, [ADR-0020](ADR-0020-audit-write-path-outbox-shared-sqs.md)).

### Negative / Trade-offs

- Owning services carry extra endpoints and a gRPC client.
- Only ECS services can use Service Connect; standalone scheduled tasks and Lambda cannot.
- A project CA and certificate rotation to manage.

## Security & Privacy Impact

The auditor validates the JWT itself even though callers already did; both sides enforce ownership. Returned entries are PII-masked.

## Cost Impact

No extra charge for Service Connect beyond the Envoy sidecar's CPU and memory. No AWS Private CA (avoids its monthly fee).

## Operational Impact

Service Connect metrics per call; gRPC error and latency alarms; certificate generation and rotation in Terraform.

## Validation

- `buf breaking` fails a pull request that would break a caller.
- An authorization test: an agent cannot read another agent's client activity through any service.
- Stopping auditor tasks in one AZ keeps reads working.
