# Target architecture: decision log

> **Status:** Proposed target architecture, not yet accepted. **Owner:** Neo Jia Wen. **Last updated:** 2026-10-01.  
> Drafted with AI assistance (Claude Code) from the team's architecture document. Verify AWS pricing, limits and service behaviour against official AWS documentation before accepting.  
> Part of the [target architecture](system-overview.md); each decision is recorded as a Proposed ADR in the [ADR index](../adr/README.md).

Every major decision in the target architecture, with what was chosen and what was not. Details are in the linked sections; each decision is recorded as a Proposed ADR (last column).

| Area | Chosen | Not chosen, and why | Details | ADR |
|---|---|---|---|---|
| Compute | ECS Fargate | EKS: about USD 73/month for the control plane alone, plus node management. | [Why ECS Fargate (and not EKS)](system-overview.md#why-ecs-fargate-and-not-eks) | [ADR-0018](../adr/ADR-0018-ecs-fargate-compute.md) |
| API entry | CloudFront → API Gateway HTTP API → VPC Link → internal ALB | A public ALB: exposes the services' load balancer to the internet and has no JWT check at the edge. | [Architecture diagram](system-overview.md#architecture-diagram), [Why each service on the diagram is included](system-overview.md#why-each-service-on-the-diagram-is-included) | [ADR-0019](../adr/ADR-0019-edge-entry-chain.md) |
| Audit writes | Transactional outbox per service + one SQS standard queue; existing request-middleware producers may save the outbox row right after the request instead, because of the cost of changing them | Synchronous gRPC writes: the auditor's availability would limit every service. Kafka/MSK: about USD 80–95/month and a cluster that cannot pause, for a single consumer. | [Audit write path: SQS, not gRPC](data-flow.md#audit-write-path-sqs-not-grpc) | [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md) |
| Audit queues | One standard queue shared by all producers (`audit-insert`) | One queue per producer: isolates bursts and proves the sender, but needs a queue, dead-letter queue, alarms and polling loop per producer. FIFO queues: ordering is not needed; they cost more and cap throughput, and duplicates are handled by `event_id` instead. | [Why one shared queue for all producers](data-flow.md#why-one-shared-queue-for-all-producers), [Why an SQS standard queue (not Kafka, not FIFO)](data-flow.md#why-an-sqs-standard-queue-not-kafka-not-fifo) | [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md) |
| Sign-in audit failures | Cognito triggers fail open: the login proceeds, and the failed event is logged to CloudWatch, alarmed and replayed | Fail closed: an SQS outage would block every login and password reset. | [Authentication events](../security/security-model.md#authentication-events) | [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md), [ADR-0025](../adr/ADR-0025-identity-cognito-mfa-pkce-service-tokens.md) |
| Ingest audit delivery | Own `ingest_outbox` table in transactions-db, relayed by the Lambda at the end of each run | Relay by transaction-service: ties ingest auditing to that service and sends events under the wrong IAM role. One shared outbox table with a producer column: separation depends on every query's filter, and database permissions cannot keep the two apart. Sending directly: loses the outbox guarantee. | [Transaction ingestion (Feature 3)](data-flow.md#transaction-ingestion-feature-3) | [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md) |
| Audit reads | gRPC through ECS Service Connect; auditor internal-only | REST through the ALB: exposes the tamper-resistant store. SQS: reads need an immediate answer. | [Audit read path: internal gRPC](data-flow.md#audit-read-path-internal-grpc) | [ADR-0021](../adr/ADR-0021-audit-read-path-grpc-service-connect.md) |
| Tamper resistance | Hash chain + separate chain-verify task + S3 Object Lock anchor + tamper-findings table | The chain alone: an admin could rewrite rows and recompute every hash. A timer inside the auditor: runs in every copy, restarts with deployments, and would let the writer write its own proof. | [Audit integrity and GDPR](../security/security-model.md#audit-integrity-and-gdpr) | [ADR-0022](../adr/ADR-0022-audit-tamper-resistance-and-crypto-shredding.md) |
| Databases | One RDS PostgreSQL instance per service, Multi-AZ standby | One shared Aurora cluster: logical isolation only. Aurora per service: over budget. | [Why one RDS instance per service: balancing cost and isolation](../database/schema.md#why-one-rds-instance-per-service-balancing-cost-and-isolation) | [ADR-0023](../adr/ADR-0023-rds-per-service-backup-no-cache.md) |
| Client data at rest | Field-level envelope encryption; per-client keys in DynamoDB wrapped by a symmetric KMS key | Plaintext keys: anyone reading the key table could decrypt all client data. Keys in clients-db: one leaked snapshot exposes both. RDS storage encryption only: no crypto-shredding. | [Client data encryption (envelope encryption)](../security/security-model.md#client-data-encryption-envelope-encryption) | [ADR-0030](../adr/ADR-0030-client-data-envelope-encryption.md) |
| Deleting clients and accounts | Soft delete: `deleted_at` is set, the row is kept and every API treats it as missing. Erasure is a separate operation | Reusing `status = 'closed'`: deleted accounts would stay visible and lose their real status, and clients have no status. Hard delete: the requirements Q&A asks for soft delete (CPM08, CPM21, CPM33). | [Right to erasure (NFR 8, GDPR)](../security/security-model.md#right-to-erasure-nfr-8-gdpr) | [ADR-0036](../adr/ADR-0036-soft-deletion-of-clients-and-accounts.md) |
| Transaction ingestion | External SFTP server; scheduled VPC-attached Lambda | AWS Transfer Family: about USD 216/month even when idle. An ECS task: slower start, more cost between runs. | [Transaction ingestion (Feature 3)](data-flow.md#transaction-ingestion-feature-3) | [ADR-0024](../adr/ADR-0024-transaction-ingestion-sftp-lambda.md) |
| Client ID check at import | None; ownership enforced on read | A lookup per import: not required by the spec, and it would make imports depend on client-service. | [Ingestion decisions](data-flow.md#ingestion-decisions) | [ADR-0024](../adr/ADR-0024-transaction-ingestion-sftp-lambda.md) |
| Schema migrations | One migration task per service before deployment | Migrations on startup: allowed for local development; needs schema rights for the app user. | [Schema migrations (db-migrate)](../database/migrations.md#schema-migrations-db-migrate) | [ADR-0028](../adr/ADR-0028-cicd-migrations-terraform.md) |
| Caching | No cache tier; dashboard uses an in-process cache | ElastiCache: cost and a failure point without a measured need. | [Databases](../database/schema.md#databases), [X-factor 2: business dashboard](x-factors.md#x-factor-2-business-dashboard) | [ADR-0023](../adr/ADR-0023-rds-per-service-backup-no-cache.md), [ADR-0033](../adr/ADR-0033-xf2-dashboard-topology-cache-audit.md) |
| Backups | RDS point-in-time recovery + AWS Backup with a cross-region copy | Point-in-time recovery only: no recovery from a regional outage. | [Why AWS Backup is included when RDS already has backups](../database/schema.md#why-aws-backup-is-included-when-rds-already-has-backups) | [ADR-0023](../adr/ADR-0023-rds-per-service-backup-no-cache.md) |
| X-factor 1 search | Tokyo web search, public terms only | Singapore (not available); third-party news API (later ADR). | [X-factor 1: event-driven market-news alerts](x-factors.md#x-factor-1-event-driven-market-news-alerts) | [ADR-0031](../adr/ADR-0031-xf1-alert-processing-search-region-boundary.md) |
