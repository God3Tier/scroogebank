# Target architecture: how each non-functional requirement is met

> **Status:** Accepted target architecture (2026-11-01). **Owner:** Neo Jia Wen. **Last updated:** 2026-10-16.  
> Drafted with AI assistance (Claude Code) from the team's architecture document. Verify AWS pricing, limits and service behaviour against official AWS documentation before accepting.  
> Part of the [target architecture](system-overview.md); each decision is recorded as an ADR in the [ADR index](../adr/README.md), which gives its status.

| NFR | How it is met |
|---|---|
| **1. Scalability / performance** (mandatory) | ECS target-tracking auto scaling on CPU and ALB requests per target (min 1, max 6 tasks). The auditor scales on SQS backlog. Database layer: storage auto-scaling, independent per-service instance resizing, and a read replica for a read-heavy service when load tests show a need ([Why one RDS instance per service: balancing cost and isolation](../database/schema.md#why-one-rds-instance-per-service-balancing-cost-and-isolation)). The ALB balances load across AZs; SQS absorbs audit bursts. dashboard-service caches each caller's answer for 3 minutes to limit fan-out. API Gateway throttles at 200 requests a second, burst 400 ([ADR-0070](../adr/ADR-0070-api-throttle-sized-for-100-concurrent-agents.md)). Load tests use k6; the 2026-11-02 results, including the specified 100-agent test over 1.5 million transactions, are in the [test strategy](../testing/test-strategy.md#results). |
| **2. Availability** (mandatory) | Tasks, the ALB, the VPC Link and the NAT gateways span two AZs. A service at its minimum of one task has no copy in the second AZ; if that task or its AZ fails, ECS starts a replacement in the healthy AZ ([ADR-0018](../adr/ADR-0018-ecs-fargate-compute.md)). Every RDS database fails over automatically to its Multi-AZ standby. SQS and S3 already span AZs. Backup and restore are covered under NFR 5. The 2026-11-02 task-failure, Auditor-outage and database-failover drills are in the [test strategy](../testing/test-strategy.md#results). |
| **3. Maintainability / extensibility** (mandatory) | One service per business area, each owning its database. OpenAPI per public service, with additive-only changes under `/api`; a versioned path is added only if a breaking change cannot be avoided. `buf breaking` on the internal gRPC contract. Audit is decoupled through events, so new features only publish events. |
| **4. Consistency** | Strong (ACID) for business data. Eventual for the audit log, list views and imports. The outbox keeps business data and audit events consistent with each other. Producers under [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md)'s exception save the outbox row just after the commit, so for them an event can be lost in a crash between the two. |
| **5. Resiliency** | Timeouts, retries with backoff and circuit breakers on outbound calls, including the SFTP connection. Failed files stay in `reports/` for the next run. SQS buffering and a dead-letter queue. ECS rolls back failed deployments automatically. **RPO:** minutes, via RDS point-in-time recovery. **RTO:** under 12 hours, by restoring an AWS Backup recovery point or a point-in-time copy into a Terraform-built stack, or, once the account allows the cross-region copy, rebuilding in ap-southeast-2; rehearsed in staging. X-factor AI calls degrade safely: the health monitor falls back to templates, a failed news search ends that run without inventing results, and model and search calls have kill switches. |
| **6. Usability** | Simple frontend, accessibility checks (axe) in CI, and a user guide in `docs/`. |
| **7. Observability** | Structured JSON logs with a request ID carried across calls, and PII masking. Custom metrics: ingestion counts, audit lag, chain verification. A CloudWatch dashboard. Alarms to SNS on 5xx errors, latency, dead-letter queue depth, oldest queue message, ingestion failure, chain mismatch and budget. client-health-monitor-service adds anonymous liveness and readiness probes, and identifier-free metrics with bounded tags in CloudWatch (`Scrooge/ClientHealth`), with dashboard panels and alarms ([X-factor 3](x-factors.md#x-factor-3-client-relationship-health-monitor)); the alert worker and the scheduled tasks alarm on a non-zero exit, and engagement-service alarms on a lagging mail dispatcher, missing holiday data and the SES bounce rate. |
| **8. Security** | [Identity and security](../security/security-model.md#identity-and-security), plus field-level envelope encryption of client data ([Client data encryption (envelope encryption)](../security/security-model.md#client-data-encryption-envelope-encryption)), GDPR crypto-shredding ([Right to erasure (NFR 8, GDPR)](../security/security-model.md#right-to-erasure-nfr-8-gdpr)), the x-factor data boundaries (only public terms leave Singapore; Bedrock receives no client identifiers for health-monitor wording; [x-factor features (Features 4–6)](x-factors.md)) and OpenAPI for every externally reachable API. CloudFront sets a Content-Security-Policy and the other security headers ([ADR-0069](../adr/ADR-0069-frontend-security-headers-and-self-hosted-fonts.md)); the OWASP ZAP results are in the [test strategy](../testing/test-strategy.md#results). |
| **9. Durability** | A synchronous Multi-AZ standby of every database, point-in-time recovery (including the client-keys table), and daily AWS Backup (a cross-region copy once the account allows it). S3 versioning. Every business change gets its audit event through an outbox and SQS, so an outage of SQS or the auditor loses none; producers under [ADR-0020](../adr/ADR-0020-audit-write-path-outbox-shared-sqs.md)'s exception (user-service, client-service and account-service today) can still lose one if they crash between the commit and the outbox write (NFR 4). Dashboard view events are best-effort, and Cognito sign-in events are sent directly with a logged, alarmed fallback ([Authentication events](../security/security-model.md#authentication-events)). A documented retention policy, with audit exports moved to Glacier by S3 lifecycle rules. |
| **10. Agility** | GitHub Actions runs CI on every pull request and push: Java and Go builds and tests (including Testcontainers), buf and oasdiff contract checks, CodeQL, OSV-Scanner, and frontend lint, tests and build. Changes are promoted `dev → staging → main` through reviewed pull requests. Deployment is manual, from the runbook, as the MFA-protected role `crm-infra-admin` ([ADR-0046](../adr/ADR-0046-human-deploy-access-mfa-role.md)): keeping the infrastructure up for automated deployments costs too much, so every deployment ends with a full teardown ([ADR-0058](../adr/ADR-0058-every-deployment-ends-with-full-teardown.md)). Each new task migrates its own database before it starts. Terraform changes are checked locally with `terraform validate` and mocked `terraform test` runs; CI does not run Terraform. |
| **11. Architecture** | The presentation layer is separate from the domain services. Everything is containerised or managed; infrastructure is defined in Terraform. |
| **12. Data segregation** | One Terraform stack per legal entity (`legal_entity = "sg"`), each with its own VPC, RDS databases, Cognito pool, KMS key and buckets, all tagged `LegalEntity`. No data is shared between stacks. The demo deploys the Singapore entity only. |
| **13. Automated testing** | Unit, contract, integration, end-to-end, authorization, failure-path, migration, load and backup-restore tests, as mapped in `docs/testing/test-strategy.md`. |
