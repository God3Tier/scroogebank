Items
-----

(DONE) 1. No way to list users
   - GET /api/users (Admin only, paged, role and enabled filters) is on dev.

(DONE, PR #83) 2. Admins cannot see agents' activity
   - The spec (Appendix 3, UI mock-up note) says "Agents can only see
     their own client activities. Admins can see the activities of all
     agents." Clients never use the CRM: these are agents' actions on
     their clients (the mock-up's "My Recent Activities").
   - Decided in ADR-0021 (accepted, PR #81): one feed, GET /api/activities
     in user-service, changes only. Admins see every agent's activities;
     agents only their own.
   - Built on task/base-features/activity-feed, on top of the branch's own
     2026-09-25 commits, and merged in PR #83:
     a. dev merged in; the branch's ListAuditLogs moved into dev's auditor
        layout.
     b. The contract moved to proto/audit/v1 (package audit.v1) with buf
        lint and buf breaking in CI. ListActivities, paged by an opaque
        page_token, replaces GetAuditLog and ListAuditLogs. The auditor's
        Dockerfile now generates its gRPC code and builds from the
        repository root.
     c. The auditor checks a Cognito token on gRPC (ADMIN or AGENT) and on
        /api/corrupted-logs (ADMIN only); agents get only their own
        entries; only changes are listed, not reads, sign-outs, failed
        attempts or system events; index on (actor_id, sequence_no);
        optional TLS on both ports. user-service forwards the caller's
        token on both.
     d. user-service: the feed is open to agents, filtered by the Cognito
        sub, with actor names; 2-second deadline, one retry on UNAVAILABLE,
        Resilience4j circuit breaker; optional TLS to the auditor. Also
        fixed: the merge had left two auditor: blocks in application.yml,
        so the service could not start; ApplicationConfigTest guards it.
   - Still to do:
     e. Infra, logged as requirements: the Service Connect alias
        auditor:50051 and AUDITOR_GRPC_TARGET; TLS certificates from the
        project CA (AUDITOR_TLS_CERT_FILE/KEY_FILE on the auditor,
        AUDITOR_GRPC_TLS_CA on user-service); COGNITO_ISSUER_URI and
        COGNITO_APP_CLIENT_ID on the auditor, and outbound HTTPS from its
        task to Cognito for the signing keys; an API Gateway route for
        /api/activities open to admins and agents.
     f. Frontend: the dashboards' "Recent Activities" panels read
        GET /api/activities, sending the user's token with
        authorizationHeader() (frontend/src/auth/session.js, PR #94).
        Locally, Vite sends only /api/users to user-service, so the panels
        need a proxy rule for /api/activities. references/TODO.txt item A8.
     g. Not built, from ADR-0021 decision 6: background callers with a
        Cognito client-credentials token and an audit/read scope. The
        auditor accepts user tokens only; build it when a caller needs it.
   - Open item 3 is resolved: the feed stays in user-service (base spec),
     not the business dashboard (x-factor).

(PARTLY DONE) 3. Audit events
   - The spec (Feature 1) requires logging of user registration, login,
     logout, password changes, account creation, account updates, role
     changes and account deactivation, with who performed the action and
     when.
   - On dev: UserAuditInterceptor publishes CREATE (including the root
     admin at startup), READ, UPDATE, DISABLE, PASSWORD_RESET, ROLE_CHANGE
     and LOGOUT. actor_id is the caller's Cognito sub. The payload holds the
     target user id, endpoint, method, status and role, never names, emails
     or field values.
   - Covered so far: registration and account creation (CREATE), account
     updates (UPDATE), role changes (ROLE_CHANGE), deactivation (DISABLE),
     admin password resets (PASSWORD_RESET), and logout (LOGOUT, which the
     frontend reports since PR #94). Login and self-service password resets
     come from the Cognito triggers (3c), built but not yet deployed.
   - To do:
     a. (DONE) Delivery. ADR-0020 is Accepted and merged (PR #75). Default
        is Option C (the outbox row commits in the business transaction);
        Option F (the row is saved in its own transaction right after the
        request) is an exception for producers that build events in request
        middleware, chosen because of the cost of changing them. Every
        service keeps an audit_outbox table and a relay that sends rows to
        SQS every 2 seconds, deleting each once SQS accepts it:
          user-service (PR #75), client-profile-management-service (#76),
          account-service (#77): exception, row saved right after the
              request.
          SFTP receiver (#78), acting as transaction-service and
              transaction-ingest: decision 3; a file's transactions and its
              event commit together; failure events are saved on their own,
              or sent straight to SQS if the database is down; the relay
              runs at the end of every poll.
        Remaining gap, accepted in ADR-0020: for the exception producers, a
        crash between the request's commit and the outbox write loses that
        event.
        To do: the infra alarm above.
     b. Corrupted-log operations. Built on
        task/base-features/corrupted-log-audit (not yet committed):
        - The interceptor now covers /api/corrupted-logs. Each event carries
          its own resource_type: USER, CORRUPTED_AUDIT_LOG, or ACCOUNT for
          transaction reads (previously mislabelled USER).
        - Reading the list has no resource id; the auditor allows that for
          READ of CORRUPTED_AUDIT_LOG only. A create takes its id from the
          request body, since the auditor's response has none.
        - The auditor checks each resource type's actions and accepts
          DELETE for CORRUPTED_AUDIT_LOG only.
        - Fixed on the way: a request refused by @PreAuthorize was audited
          with status 200, because Spring Security sets the 403 after the
          interceptor runs. This affected every admin-only endpoint. Denials
          are now recorded as 403, and unhandled exceptions as 500.
        When deploying: release the auditor no later than user-service.
     c. Login and self-service password reset happen in Cognito, not here.
        They need the PostAuthentication and
        PostConfirmation_ConfirmForgotPassword triggers (ADR-0020 decision
        4). Built in PR #90 (services/cognito-triggers, ADR-0040); the
        function and the user pool triggers come with the infra.
   - Open: UPDATE events record that an update happened, not which fields
     changed. That meets "who and when". Recording before and after values
     would put names into the audit chain, which dev's auditor README rules
     out.

(DONE) 4. Role cannot be changed
   - PATCH /api/users/{id}/role is on dev. The root admin's role cannot be
     changed (403).
   - Audited as ROLE_CHANGE since PR #73. The event records the new role,
     not the previous one.
   - When deploying: release the auditor no later than user-service, or
     role-change events go to the dead-letter queue.
   - Open: whether an admin may change their own role (still allowed).

(DONE, PR #74 and #94) 5. No logout endpoint
   - The spec requires logout to be audited. Cognito ends the session
     itself but has no sign-out trigger, so the frontend has to report it
     (ADR-0025).
   - Decided 2026-10-09: the frontend revokes the refresh token with Cognito
     itself and then tells user-service; the backend revokes nothing.
   - On dev since PR #74: POST /api/users/me/logout (any signed-in user, no
     body; 204, or 404 if the token's sub has no user) is published as
     LOGOUT by UserAuditInterceptor against the caller's own user. The
     auditor accepts LOGOUT. The README section "Logout" documents the
     sign-out sequence.
   - Trade-off accepted: the event records what the frontend reports, not a
     verified revocation. A failed or skipped call loses the event; the
     sign-out still happens.
   - To do:
     a. When deploying: release the auditor no later than user-service, or
        logout events go to the dead-letter queue.
     b. (DONE, PR #94) Frontend sign-out, in frontend/src/auth/signOut.js:
        POST /api/users/me/logout with the access token first, then revoke
        the refresh token at Cognito's /oauth2/revoke, then drop the local
        tokens and redirect to Cognito's /logout. Each step runs even if the
        one before fails or takes over 5 seconds. The order changed from
        the 2026-10-09 plan (revoke first) so the audit call never depends
        on a gateway accepting a token whose refresh token was revoked.
        Not yet run end to end against Cognito (references/TODO.txt item A4).
     c. Infra, logged as requirements: the app client needs token revocation
        enabled (the default for new clients). The API Gateway check
        planned here is no longer needed, since the audit call comes first.
     d. (DONE, PR #93) ADR-0025, now Accepted, records this flow (decision
        5) and the trade-off above.
   - Alternative not taken: CloudTrail does record sign-outs (checked
     2026-10-09 in the AWS Cognito CloudTrail docs): RevokeToken API calls,
     and the classic Hosted UI's /logout as a "Logout" event, with the
     user's sub. The docs list no sign-out event for the newer managed login
     pages. CloudTrail is not the audit hash chain, so using it would need a
     pipeline from the trail into the audit queue (more infra). ADR-0025
     records this as the option not chosen.
